# sprint-10-stripe-pro-and-usage · undefined — Tareas

Checklist de implementación. El agente marca [x] al completar; los gates verifican.

- [x] (T1) El navegador recibe únicamente identificadores publicables estrictamente necesarios; STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET y SUPABASE_SERVICE_ROLE_KEY permanecen en módulos server-only, no usan NEXT_PUBLIC_ y no aparecen en bundles, respuestas, logs ni fixtures.  ↔ R1
- [x] (T2) `POST /api/stripe/checkout` y `POST /api/stripe/portal` reciben exactamente `{returnTo:"/app/pro"}`, exigen sesión Supabase y responden `{ok:true,data:{url},error:null}`. Checkout compra exclusivamente el precio configurado server-side en `STRIPE_PRO_PRICE_ID`; reutiliza el único customer canónico, crea uno idempotentemente si no existe y rechaza varios con `CUSTOMER_AMBIGUOUS`. Solo se acepta la ruta relativa exacta `/app/pro`, y el servidor construye los retornos desde `NEXT_PUBLIC_APP_URL`.  ↔ R2
- [x] (T3) Cada Checkout Session nueva guarda `metadata.supabase_user_id`. Durante la transición, un customer sin esa metadata solo puede resolverse desde `customer.metadata.firebase_uid` contra exactamente una fila `legacy_id_map` con `source='FIREBASE'`, `entity_type='auth_user'` y ese `legacy_id`; cero o varias coincidencias devuelven `CUSTOMER_NOT_FOUND` o `CUSTOMER_AMBIGUOUS` y no escriben dominio.  ↔ R3
- [x] (T4) El webhook verifica la firma sobre el cuerpo crudo antes de consultar o escribir la base; una firma ausente o inválida devuelve 400 y deja sin cambios stripe_events, subscriptions, entitlements, usage y auditoría.  ↔ R4
- [x] (T5) stripe_events impone UNIQUE(event_id). El primer procesamiento persiste evento, resultado y timestamps atómicamente; replays devuelven 200 y reproducen el primer resultado sin repetir efectos. El orden total es `(event.created,event.id)` con comparación lexicográfica ascendente del ID cuando `created` coincide; solo una tupla estrictamente mayor puede reemplazar el estado aplicado.  ↔ R5
- [x] (T6) `subscriptions` contiene exactamente una fila canónica por user_id y customer; `stripe_customer_id` y `stripe_subscription_id` son únicos cuando no son null. Si Stripe devuelve varias subscriptions, se elige la de mayor `(event.created,event.id)` y se registra la anomalía; esa única fila determina entitlement y reconcile. El cursor se compara por usuario/fila canónica, no globalmente.  ↔ R6
- [x] (T7) El webhook procesa `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed` e `invoice.payment_succeeded`; otros tipos se registran como `ignored`. Los eventos invoice recuperan la subscription referenciada y aplican su estado actual con el cursor del evento; si el estado no cambió solo avanzan cursor/event ledger. `active` y `trialing` conceden Pro; `past_due`, `canceled`, `unpaid`, `incomplete`, `incomplete_expired` y `paused` son Free.  ↔ R7
- [x] (T8) `POST /api/stripe/admin/override` es server-to-server, exige `Authorization: Bearer BILLING_ADMIN_SECRET`, recibe `{userId,value:boolean|null,reason}` y deriva actor `billing-admin`. `true` fuerza Pro, `false` fuerza Free y `null` elimina override y vuelve a Stripe/legacy; override tiene precedencia. `before` y `after` auditan `{override,plan,status,source}` completos antes/después.  ↔ R8
- [x] (T9) `POST /api/usage/consume` recibe exactamente `{feature,idempotencyKey}`, deriva user_id y periodo UTC, admite límites 5/5/10 y responde para permitido `{ok:true,data:{allowed:true,feature,period,used,limit,remaining,duplicate},error:null}`. La clave se scoped por `(user_id,feature,period)`; reutilizarla en otro feature o mes es una operación distinta. Dentro del mismo scope, el replay permitido devuelve los contadores originales con `duplicate:true`.  ↔ R9
- [x] (T10) Para Free, las primeras N reservas nuevas se permiten y N+1 devuelve siempre HTTP 429 `{ok:false,data:null,error:{code:"QUOTA_EXCEEDED",message,retryable:false}}`; su replay reproduce exactamente ese 429, sin campo duplicate público. La reserva ocurre después de validación/cache y justo antes de invocar el proveedor; una vez autorizada no se libera: cualquier éxito o error posterior del proveedor consume. Cancelación antes de reservar, validación, cache hit y replay permitido no incrementan. Concurrencia nunca supera N.  ↔ R10
- [x] (T11) Para Pro, consume_usage autoriza sin incrementar ni reservar contadores Free. Un downgrade posterior empieza con el contador Free que existía antes del periodo Pro y nunca imputa retroactivamente operaciones realizadas mientras el entitlement era Pro.  ↔ R11
- [x] (T12) El cambio de mes se decide con reloj UTC de base de datos dentro de la misma transacción; el cliente no puede proporcionar ni alterar period, límite, contador o entitlement.  ↔ R12
- [x] (T13) El Paywall vive en `/app/pro` y representa loading, free, trialing/active, past_due, canceled y error. Los parámetros exactos `?checkout=success` y `?checkout=cancel` solo muestran un aviso y fuerzan `GET /api/stripe/entitlement`; nunca conceden Pro. Red, timeout, 429 y 5xx muestran estado recuperable con botón `Reintentar`; 401 redirige a `/login?error=session_expired&returnTo=%2Fapp%2Fpro`; errores no reintentables muestran su código seguro sin reintento automático.  ↔ R13
- [x] (T14) El Portal solo se crea para el customer canónico del usuario autenticado. Customer ausente o ambiguo devuelve respectivamente 404 `CUSTOMER_NOT_FOUND` o 409 `CUSTOMER_AMBIGUOUS`, sin crear otro customer ni revelar identificadores ajenos.  ↔ R14
- [x] (T15) `POST /api/stripe/reconcile` es server-to-server, exige `Authorization: Bearer STRIPE_RECONCILE_SECRET`, recibe `{stripeCustomerId}` y responde `{ok:true,data:{customerId:string,userId:string,status:"active"|"trialing"|"past_due"|"canceled"|"unpaid"|"incomplete"|"incomplete_expired"|"paused"|"none",applied:boolean,eventCursor:{created:number,id:string}|null},error:null}`. `applied` indica que cambió fila/cursor. Customer ausente devuelve 404 `CUSTOMER_NOT_FOUND`; mapping o subscriptions ambiguas, 409 `CUSTOMER_AMBIGUOUS`. Es repetible sin duplicados.  ↔ R15
- [x] (T16) Las migraciones son aditivas y preservan user_entitlements, contadores existentes, Firebase, Expo y mappings legacy. El backfill es idempotente y el rollback del deployment mantiene legibles todos los datos económicos y de uso sin down migrations destructivas.  ↔ R16
- [x] (T17) Tests sin red real cubren checkout autenticado/no autenticado, redirects allowlisted, portal válido/sin customer, firma inválida sin escrituras, replay, concurrencia y orden de webhooks, mapping legacy ausente/único/ambiguo, active/trialing/past_due/canceled, override administrativo auditado, límites 5/5/10 con N+1 concurrente, replay de usage, frontera mensual UTC, bypass Pro y downgrade posterior.  ↔ R17
- [x] (T18) Playwright verifica todos los estados del Paywall y los retornos success/cancel contra estado canónico; pgTAP verifica constraints, RLS, idempotencia y concurrencia; un test de artefactos confirma que secretos Stripe no aparecen en bundle cliente, respuestas ni logs saneados.  ↔ R18
- [x] (T19) `GET /api/stripe/entitlement` exige sesión y responde `{ok:true,data:{plan:"free"|"pro",status:"active"|"trialing"|"past_due"|"canceled"|"unpaid"|"incomplete"|"incomplete_expired"|"paused"|"none",source:"override"|"stripe"|"legacy"|"default",currentPeriodEnd:string|null,cancelAtPeriodEnd:boolean},error:null}`. Override conserva el status Stripe visible pero determina plan/source. Todas las rutas usan el mismo sobre y errores `{ok:false,data:null,error:{code,message,retryable}}`.  ↔ R19
